# Архитектура приложения GameStore

## 1. Общая информация

GameStore — веб-приложение для просмотра каталога
видеоигр и публикации новых игр.

Приложение реализовано с использованием клиент-серверной архитектуры.

Основные технологии:

- Frontend: React + Vite
- Backend: Python + FastAPI
- База данных: PostgreSQL
- Управление базой данных: pgAdmin
- Взаимодействие с базой данных: SQLAlchemy
- Аутентификация: JWT (JSON Web Tokens)
- Контейнеризация: Docker + Docker Compose

## 2. Архитектура компонентов

### 2.1 Frontend (Клиентская часть)

Используемые технологии:

- React
- Vite
- JavaScript
- CSS

Основные задачи:

- Отображение интерфейса GameStore.
- Отображение каталога игр.
- Регистрация новых пользователей.
- Авторизация существующих пользователей.
- Хранение JWT-токена в sessionStorage.
- Отображение информации об аккаунте.
- Отображение функций, доступных только издателям.
- Предоставление формы для публикации игр.
- Взаимодействие с backend через HTTP-запросы.

Основные файлы:

- App.jsx
- App.css
- main.jsx

### 2.2 Backend (Серверная часть)

Используемые технологии:

- Python
- FastAPI
- SQLAlchemy
- Pydantic
- PyJWT
- Драйвер PostgreSQL

Основные задачи:

- Обработка HTTP-запросов от frontend.
- Проверка и валидация входящих данных.
- Регистрация новых аккаунтов.
- Проверка учётных данных при входе.
- Создание JWT-токенов.
- Аутентификация пользователей.
- Проверка ролей и прав доступа.
- Получение списка игр из PostgreSQL.
- Публикация новых игр.
- Отправка ответов в формате JSON.

### 2.3 База данных

ER-диаграмма базы данных расположена в docs/ER-diagram.

Для хранения информации используется PostgreSQL. 

Для управления базой данных используется инструмент pgAdmin.

SQLAlchemy используется для взаимодействия между backend и базой данных.

База данных GameStore содержит следующие основные таблицы:

- accounts — учётные записи пользователей;
- games — каталог видеоигр;
- dlcs — дополнения к играм;
- library — пользовательские игровые библиотеки;
- game_reviews — отзывы и оценки;
- developers — разработчики;
- publishers — издатели;
- game_developers — связь игр и разработчиков;
- game_publishers — связь игр и издателей.

Основные задачи базы данных:

- Хранение аккаунтов пользователей.
- Хранение хешей паролей.
- Хранение ролей пользователей.
- Хранение информации об играх.
- Хранение игровой библиотеки пользователей. 
- Хранение отзывов пользователей.
- Хранение информации о разработчиках и издателях.

Связи между таблицами реализованы с помощью
первичных и внешних ключей.

Для обеспечения целостности данных применяются
ограничения UNIQUE, NOT NULL и CHECK.


## 4. Взаимодействие компонентов

Взаимодействие между клиентской и серверной частями GameStore осуществляется посредством HTTP-запросов. Frontend отправляет запросы к API с помощью Fetch API, а backend обрабатывает их с использованием FastAPI.

Для обмена данными используется формат JSON. SQLAlchemy обеспечивает взаимодействие backend с базой данных PostgreSQL.

### 4.1. Получение каталога игр

При открытии главной страницы frontend отправляет GET-запрос на endpoint `/api/games`.

Последовательность действий:

1. Frontend React отправляет HTTP GET-запрос.
2. Backend FastAPI принимает запрос и вызывает соответствующий обработчик (endpoint).
3. SQLAlchemy выполняет SQL-запрос к таблице `games` в PostgreSQL.
4. PostgreSQL возвращает найденные записи.
5. Backend преобразует полученные данные в формат JSON.
6. Frontend получает ответ и отображает каталог игр.

Просмотр каталога доступен без авторизации (Browsing as guest).

### 4.2. Регистрация и авторизация пользователя

**Регистрация:**

1. Пользователь заполняет форму регистрации на frontend.
2. Frontend отправляет POST-запрос на endpoint `/api/register` с данными пользователя.
3. Backend FastAPI проверяет входящие данные с помощью Pydantic.
4. Backend передаёт данные в PostgreSQL через SQLAlchemy.
5. Пароль хешируется с помощью расширения `pgcrypto`.
6. Информация о новом аккаунте сохраняется в таблице `accounts`.
7. Backend возвращает результат регистрации в формате JSON.

Новым аккаунтам автоматически присваивается роль `user`.

**Авторизация:**

1. Пользователь вводит имя пользователя и пароль.
2. Frontend отправляет POST-запрос на endpoint `/api/login`.
3. Backend проверяет учётные данные в PostgreSQL.
4. При успешной проверке backend создаёт JWT-токен.
5. Frontend получает токен и сохраняет его в `sessionStorage`.
6. При последующих запросах, требующих авторизации, frontend передаёт токен в HTTP-заголовке `Authorization`.

### 4.3. Публикация игры издателем

Для публикации игры пользователь должен войти в аккаунт с ролью `publisher`.

Последовательность действий:

1. Пользователь авторизуется в приложении.
2. Frontend получает JWT-токен и отображает функции, доступные издателю.
3. Издатель заполняет форму с информацией об игре.
4. Frontend отправляет POST-запрос на endpoint `/api/games`, передавая данные игры и JWT-токен.
5. Backend FastAPI проверяет входящие данные и передаёт токен для проверки.
6. Backend проверяет подпись и срок действия JWT-токена.
7. Backend получает информацию об аккаунте из PostgreSQL и проверяет его текущую роль.
8. Если пользователь имеет роль `publisher`, SQLAlchemy выполняет INSERT-запрос в таблицу `games`.
9. PostgreSQL сохраняет новую игру и возвращает результат операции.
10. Backend отправляет ответ frontend.
11. После успешной публикации frontend повторно загружает каталог игр, чтобы отобразить новую запись.

Если токен недействителен или у пользователя недостаточно прав (role: `user`), backend отклоняет запрос.

### 4.4. Взаимодействие с базой данных

Backend использует SQLAlchemy для выполнения операций с PostgreSQL.

В текущей реализации применяется SQLAlchemy Core:
- `create_engine()` — создание движка для управления подключениями к базе данных.
- `engine.connect()` — получение соединения для выполнения запросов.
- `engine.begin()` — выполнение операций в рамках транзакции.
- `text()` — подготовка SQL-запросов.
- `connection.execute()` — выполнение SQL-запросов.

Для получения и изменения данных используются SQL-команды `SELECT`, `INSERT` и другие необходимые операции.

SQL-запросы используют параметры, позволяющие передавать значения отдельно от SQL-кода.

### 4.5. Обработка ответов и ошибок

После обработки каждого HTTP-запроса backend возвращает frontend ответ с соответствующим HTTP-статусом и данными в формате JSON.

В случае успешного выполнения операции frontend обрабатывает полученный результат и обновляет интерфейс.

При возникновении ошибки backend возвращает соответствующий статус:
- `400 Bad Request` — ошибка при обработке переданных данных или операции.
- `401 Unauthorized` — отсутствует действительная авторизация.
- `403 Forbidden` — у пользователя недостаточно прав доступа.
- `503 Service Unavailable` — ошибка при взаимодействии с базой данных.

Frontend обрабатывает ошибки и отображает пользователю соответствующие сообщения.

## 10. Безопасность
В приложении предусмотрены следующие меры безопасности:

- Пароли хранятся в виде хешей.
- Для аутентификации используется JWT.
- JWT-токены имеют ограниченный срок действия (60 минут).
- Backend проверяет аутентификацию пользователей.
- Backend проверяет права издателей перед публикацией игр.
- SQL-запросы используют параметры.
- Данные для подключения к базе данных хранятся в файле .env.
- Файлы локальной базы данных исключены из Git.
